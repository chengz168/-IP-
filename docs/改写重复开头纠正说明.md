# 改写重复开头纠正说明

日期：2026-11-28。

## 实际问题

桌面工作台的“改写文案”提示“后文重复了保留开头，当前文案保留”，右侧无新正文。失败记录显示，3232 字转写缺少句末标点，固定首段后的 3203 字形成一个信息单元；模型在该单元前又输出了固定首段。现有校验拒绝重复是正确的，但校验异常直接结束了任务，没有进入已有的限定纠正流程。

## 修复范围

- 复用现有 `generateRewrite`、信息单元组装、正文生成器及两次调用上限，无新增依赖或模型。此次是本项目的请求协议与错误恢复缺陷，继续现有实现，不引入外部工程。
- 保留来源模板原件，在实际 system 请求末尾明确执行分工：首段已经由应用保留，模型只返回各编号的后文。请求补充说明记录为 `executionProtocol`，不冒充原软件云端内部提示词。
- 首次完整返回后的 JSON、信息单元等校验失败允许纠正一次。纠正仅回填错误原因，不把长篇失败正文再次塞入上下文。已存在的完全照抄和长度偏差纠正仍共用同一个两次上限。
- 不替换原始回包，不放宽数字、单元齐全及否定反转校验。持续失败时保留两次响应；连接失败、输出截断或取消不自动重新请求。
- 实际首次修复重跑中，模型两次仍基本照抄原稿：首次重复开头，纠正后正文与原文相同，候选被正确拒绝。因此进一步复用已有整篇正文生成器：参考模板原稿至少 1000 字，且单个无句末标点的单元超过 600 字时，改为按原有论点组织自然段，不强制单一超长 JSON 字符串；正常句段继续逐单元改写。
- 长转写正文同样校验重复开头、JSON/代码块、数字及型号新增/遗漏，保留原稿的疑问、假设与主观判断，不补全人物或日期。普通模板维持既有执行，大幅扩写与长转写共用正文生成器。两种模式的纠正都只携带错误原因，避免重复塞入完整失败稿。
- 首次正文生成实测依然回显原文，因此长转写进一步使用独立的本地执行副本，明确首段分工、口语重组和事实边界，不再携带相冲突的首段照抄命令。原模板完整留在输入快照中，执行差异以 `local-long-transcript-rewrite-v1` 记录；原稿后文用 `<source>` 边界包裹，首段不再混入待改写资料，用户补充要求及创作预设仍透传。未更换模型、修改共享模型模板或调整正式模型配置。
- 后续实测模型已返回改写段落，但仍多带一个独立固定首行。长转写因此复用扩写原有的精确首行合并：仅当首行与应用固定开头逐字相等时，合并一行并由应用拼接一次，原回包完整留证，同时记录 `remove-exact-opening-line`。第一行含其他正文、改写了开头，或合并后仍重复开头的情况继续拒绝，不删除任意正文前缀。
- 结果仍通过原有的过期检查与文案质量检查后才写入改写区，不自动确认使用。
